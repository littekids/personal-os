# Personal OS 产品架构设计

> 不是另一个工具，是你的数字根基。
> 设计标准：10年后回头看，这个设计是否仍然成立？

---

## 1. 产品核心理念

### 一句话定义

**Personal OS = 一个随你成长的、AI驱动的个人数字基础设施。**

### 灵魂三问

| 问题 | 回答 |
|------|------|
| 它是什么？ | 一个**长期对话伙伴**，通过持续交流理解你、帮助你、陪你成长 |
| 它不是？ | 不是工具集合、不是笔记软件、不是待办清单、不是AI套壳 |
| 为什么存在？ | 每个人的信息、决策、记忆散落在无数App里。你需要一个**属于你自己的**统一层 |

### 三条铁律（10年后不变）

**铁律一：数据主权不可侵犯**
- 全部数据存储在用户自己的数据库里
- 可随时导出、迁移、删除
- 绝不卖数据、绝不用数据训练模型（除非用户主动选择）
- 支持自部署

**铁律二：对话即界面**
- 不追求仪表盘、复杂UI、功能堆砌
- 一切操作通过自然语言完成
- 图形界面是对话的补充，不是替代
- 用户在对话中自然表达需求，系统渐进式响应

**铁律三：随你成长，而非替代你**
- AI是副驾驶，不是自动驾驶
- 记录你的决策过程，而非替你决策
- 越来越懂你，但不替你做你不愿做的事
- 10年后，你的Personal OS里有你10年的人生轨迹

### 与现有产品的本质区别

| | Notion | ChatGPT | 传统OS | Personal OS |
|---|---|---|---|---|
| 核心隐喻 | 文档 | 对话 | 桌面 | **家** |
| 数据结构 | 页面/块 | 对话线程 | 文件/文件夹 | **记忆图谱** |
| 时间观 | 无时间性 | 短期对话 | 创建/修改时间 | **生命时间线** |
| 与用户关系 | 工具 | 助手 | 平台 | **长期伴侣** |
| 数据归属 | 云端 | 云端 | 本地 | **用户持有** |

## 2. 用户旅程

### 第一层：相遇（第1-3天）

```
用户说："我最近工作压力很大，感觉什么都做不完"
    ↓
AI人格回应：共情 + 识别潜在需求 + 温和引导
    "听起来你在处理很多事情。要不要我们先一起理一理你手头的事？
     不用现在排序，就是随便说说都有什么。"
    ↓
用户在对话中自然列出工作内容
    ↓
AI人格：识别到"任务管理"需求，激活【任务感知】模块
    "我帮你把这些记下来了——一共7件事。
     想不想我们每天花5分钟过一遍？不复杂，就是聊聊今天重点做哪个。"
```

**这一层的关键设计意图**：
- 用户不需要知道任何功能、不点任何按钮
- AI通过对话自然识别需求
- 第一个模块（任务）是被"聊出来"的，不是被"开启"的

### 第二层：理解（第4-30天）

```
持续对话中，AI开始建立用户画像：

"根据我们这段时间的交流，我注意到几个模式：
  - 你周一到周三精力最好，周四开始下滑
  - 下午2-4点是你的深度工作时间
  - 创意类工作在上午做得更好
  - 你对 deadline 有很强的责任感，但也会因此焦虑
  
  要不要试试把重要工作排到上午，周四下午留白？
  当然，这些只是我观察到的，你最有发言权。"
```

**这一层的关键设计意图**：
- AI开始从对话中提取模式，形成用户画像
- 画像对用户**完全透明**且可修正
- 用户感到"被理解"，而非"被监控"

### 第三层：沉淀（第31-90天）

```
用户画像逐渐丰富，记忆系统开始建立关联：

"3个月前你提到想学 Rust，这两天你在解LeetCode也用了Rust。
 当时你说是因为想做系统编程——现在这个方向还有兴趣吗？
 如果还有的话，我想帮你整理一条学习路径。"
```

**这一层的关键设计意图**：
- 跨时间的记忆关联，让用户感到"原来我已经走了这么远"
- AI帮助用户看到自己的成长轨迹
- 这是形成长期粘性的核心——用户不想丢失这个"懂自己的人"

### 第四层：融合（第91天以后）

```
Personal OS 成为用户思维的外延：

用户："下周去东京出差，帮我看看要注意什么"
AI人格：
  "你2019年去过一次日本，不过那次是大阪。你当时记录的几点：
    1. 西瓜卡很方便（现在还适用）
    2. 你吃不惯纳豆（笑）
    3. 当时你买了很多手办...
   
   这次去东京，结合你现在的口味偏好变化和日程，
   我整理了几点建议。另外你最近在控制饮食，
   我标记了需要注意的餐厅类型。"
```

**这一层的关键设计意图**：
- 系统连接过去和现在，让用户的生活数据产生复利价值
- 不是冷冰冰的信息检索，而是带有人情味的陪伴
- 用户的数据越积累，系统越不可替代

## 3. 核心模块设计

### 模块哲学：生而不是装

传统软件是"安装功能"。Personal OS 的模块是**生长出来的**——
用户在生活中遇到某个场景，AI在对话中识别需求，模块随之被激活。

一个模块从生到长的生命周期：

```
种子期 → 萌芽期 → 生长期 → 成熟期
(需求识别) (基础形态) (功能深化) (稳定服务)
```

### 第一批核心模块（按优先级）

#### M1：记忆系统（基础模块，所有模块的底座）

| 属性 | 说明 |
|------|------|
| 一句话 | 记住关于用户的一切，并在合适的时机回响 |
| 核心能力 | 事实记忆（用户说过什么）、模式识别（行为规律）、情感记忆（偏好和厌恶） |
| 用户价值 | "它记得我去年提过的事，我不用重复自己" |
| 设计难点 | 什么该记？什么不该记？什么时候该提？什么时候不该提？ |

**记忆分层模型**：

```
Layer 0 — 瞬态记忆：当前对话上下文（对话结束即消失）
Layer 1 — 短期记忆：最近7天的对话要点
Layer 2 — 长期事实：用户基本信息、偏好、人际关系
Layer 3 — 模式记忆：行为规律、决策模式、情绪周期
Layer 4 — 价值观记忆：深层信念、人生目标、不可妥协的原则
```

每层有不同的衰减策略和提取策略。

#### M2：时间感知系统

| 属性 | 说明 |
|------|------|
| 一句话 | 帮助用户感知、规划和回顾时间 |
| 核心能力 | 日程识别、习惯追踪、周期性回顾 |
| 用户价值 | "它比我自己更清楚我的节奏" |
| 激活条件 | AI在对话中识别到时间相关表达 |

**设计原则**：用户不需要"写日程"，而是在对话中提到"下周有个会"，系统自然捕捉。

#### M3：知识库

| 属性 | 说明 |
|------|------|
| 一句话 | 用户个人知识的积累和检索 |
| 核心能力 | 链接保存、笔记记录、知识关联、定向回顾 |
| 用户价值 | "我读过的、想过的，都能找回来" |
| 激活条件 | AI在对话中识别到"这个值得记下来"的信号 |

**设计原则**：不是Evernote替代品。用户说"这篇文章不错，帮我存一下"，系统处理存储、标签、关联。

#### M4：决策记录

| 属性 | 说明 |
|------|------|
| 一句话 | 记录用户的重大决策及其背景和结果 |
| 核心能力 | 决策上下文记录、结果追踪、定期回访 |
| 用户价值 | "我知道自己做了什么决定，以及为什么" |
| 激活条件 | AI识别到用户在做选择 |

**设计原则**：不替用户决策。只记录决策时的考量、情绪、预期结果，事后可回看。

#### M5：健康感知（种子期）

| 属性 | 说明 |
|------|------|
| 一句话 | 关注用户的身心健康基线 |
| 核心能力 | 情绪趋势、睡眠/运动感知、压力预警 |
| 用户价值 | "它在我累之前提醒我休息" |
| 激活条件 | 用户在对话中表达情绪或身体状态 |

**设计原则**：非医疗、非监控、温和提醒。

## 4. 数据库结构规划

### 设计原则

1. **以用户时间线为核心**：所有数据都挂在时间线上
2. **对话是一切数据的第一入口**：无论是记忆、任务、知识，最初都来自对话
3. **Schema随模块演进**：不为未开发的功能建表
4. **可审计、可导出**：每条数据都有时间戳、来源、类型标记

### 核心表结构（第一版）

```
┌──────────────────────────────────────────────────────────┐
│                       users                              │
│  id | username | email | password_hash | created_at      │
│  用户基础信息                                            │
└────────────┬─────────────────────────────────────────────┘
             │
             │ 1:N
             ▼
┌──────────────────────────────────────────────────────────┐
│                    conversations                         │
│  id | user_id | title | model | created_at | updated_at  │
│  一次持续的对话会话                                       │
└────────────┬─────────────────────────────────────────────┘
             │
             │ 1:N
             ▼
┌──────────────────────────────────────────────────────────┐
│                      messages                            │
│  id | conversation_id | role | content | metadata(jsonb) │
│  | created_at                                            │
│  对话中的每一条消息                                       │
└────────────┬─────────────────────────────────────────────┘
             │
             │ AI提取
             ▼
┌──────────────────────────────────────────────────────────┐
│                      memories                            │
│  id | user_id | type | content | embedding(vector)       │
│  | source_message_id | importance(1-5) | layer(0-4)     │
│  | expires_at | created_at | updated_at                  │
│  从对话中提取的记忆单元（记忆系统的物理载体）             │
└────────────────────┬─────────────────────────────────────┘
                     │
                     │ 关联
                     ▼
┌──────────────────────────────────────────────────────────┐
│                   memory_links                           │
│  id | source_memory_id | target_memory_id | relation_type│
│  记忆之间的关联图谱                                       │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│                    user_profile                           │
│  id | user_id | trait_key | trait_value | confidence     │
│  | evidence_messages(jsonb) | created_at | updated_at    │
│  用户画像 — 动态生长，每条特质都有置信度和来源证据        │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│                       modules                            │
│  id | user_id | module_key | status(种子/萌芽/生长/成熟) │
│  | config(jsonb) | activated_at                          │
│  用户已激活的模块及生命周期状态                           │
└──────────────────────────────────────────────────────────┘
```

### Sprint 1 建什么表？

**只建 messages 表**。其他表在需要时才建。过度设计数据库是早期项目的第一杀手。

## 5. AI 人格系统设计

### 为什么需要人格系统？

用户每天换一个AI工具，但 Personal OS 的目标是陪伴用户10年。

**人格 = 一致性 + 可预测性 + 情感连接**。

用户需要感觉每次对话都是在和"同一个人"交流，即使底层模型换了。

### AI人格定义

**名字**：待定（可以用户自己命名，增加归属感）

**核心特质**：

| 维度 | 设定 |
|------|------|
| 语气 | 温暖、平静、略带幽默，但不过分热情 |
| 角色 | 像一个懂你的老朋友 + 思维外脑 |
| 主动性 | 中等 — 不打扰但会适时提醒、提问、回顾 |
| 诚实度 | 不知道就说不知道，不编造 |
| 记忆感 | 在合适的时候提起过去聊过的事 |
| 距离感 | 亲密但尊重边界，不假装是人类 |

### 人格实现方案

```
┌─────────────────────────────────────────┐
│            System Prompt 层             │
│  - AI人格基础定义                       │
│  - 核心行为准则                          │
│  - 对话风格指南                          │
├─────────────────────────────────────────┤
│          动态上下文注入层                │
│  - 用户画像摘要（动态更新）              │
│  - 近期对话摘要（最近7天）               │
│  - 关联记忆（与当前话题相关的历史记忆）   │
│  - 当前激活模块的能力说明                │
├─────────────────────────────────────────┤
│        工具/模块调用层                   │
│  - 可用的模块工具                        │
│  - Function Calling 定义                │
│  - 模块响应格式                          │
└─────────────────────────────────────────┘
```

### 人格一致性保障

| 问题 | 方案 |
|------|------|
| 换了模型，人格会不会变？ | System Prompt + 用户画像共同约束；定期人格快照审计 |
| 如何保证不胡说？ | 所有用户相关事实从数据库提取，不依赖模型"记忆" |
| AI会不会"太主动"？ | 主动性可调节（用户可设置1-5级）；默认偏保守 |

### 用户画像的数据模型

```json
{
  "user_id": "xxx",
  "traits": [
    {
      "key": "work_style",
      "value": "深度工作偏好型，上午效率高",
      "confidence": 0.85,
      "evidence_count": 12,
      "first_observed": "2026-07-26",
      "last_updated": "2026-08-15"
    },
    {
      "key": "communication_style",
      "value": "喜欢直接反馈，不喜欢绕弯",
      "confidence": 0.92,
      "evidence_count": 8,
      "first_observed": "2026-07-28",
      "last_updated": "2026-08-10"
    }
  ],
  "summary": "一位注重效率的工程师，偏好直接沟通，上午创造力最佳..."
}
```

画像的每一条都有置信度、证据数量、观察时间，用户随时可以看、可以改。

## 6. MVP 开发路线

### MVP 的定义标准

MVP 不是"功能最少"，而是**能验证核心假设的最小产品**。

Personal OS 的核心假设只有一个：**人们愿意持续和一个AI对话，如果这个AI能记住他们说过的话。**

如果这个假设不成立，后面所有功能都白做。

### Sprint 重新规划

```
Sprint 1 ✅ — 脚手架 & 基础对话
  已完成：项目结构、基础聊天UI、FastAPI骨架

Sprint 2 — 接入AI + 基础记忆
  目标：验证核心假设
  功能：
    - 接入 Claude API（流式对话）
    - 对话历史持久化（messages表）
    - 简单上下文注入（最近N条消息）
  不做：
    - ❌ 用户认证（先单用户）
    - ❌ 记忆系统（Sprint 3）
    - ❌ 任何模块

Sprint 3 — 记忆系统 v0
  目标：让AI"记住"用户说过的重要信息
  功能：
    - 记忆提取（从对话中自动提取关键事实）
    - 记忆注入（将相关记忆注入System Prompt）
    - 记忆管理界面（用户查看/编辑/删除记忆）
  衡量标准：
    - 用户说"我之前提过...”——AI能接上
    - 用户不需要重复说过的话

Sprint 4 — 用户画像
  目标：AI开始理解用户的行为模式
  功能：
    - 画像特征提取
    - 习惯/偏好识别
    - 画像透明度面板
  不做：
    - ❌ 模块系统
    - ❌ 多用户

Sprint 5 — 模块系统架构
  目标：建立可扩展的模块框架
  功能：
    - 模块注册/激活机制
    - 第一个模块：任务感知（M2简化版）
    - 模块与记忆系统互通

Sprint 6+ — 按反馈迭代
  根据真实用户反馈决定优先级
```

### 每个 Sprint 的 Done 定义

| Sprint | 可演示的成果 |
|--------|-------------|
| Sprint 2 | 与AI流畅对话，历史消息跨刷新保持 |
| Sprint 3 | 用户说一件事，第二天AI还能想起来 |
| Sprint 4 | AI主动发现用户的习惯模式 |
| Sprint 5 | 用户说"帮我记个任务"，系统自动捕捉 |

### 技术决策记录（Sprint 1 已做）

| 决策 | 选择 | 理由 |
|------|------|------|
| 前端框架 | Next.js 15 | React生态、SSR支持、中国社区活跃 |
| 后端框架 | FastAPI | 异步原生、类型安全、AI生态整合方便 |
| 数据库 | PostgreSQL | 成熟、支持jsonb/vector、自部署友好 |
| ORM | SQLAlchemy 2.0 | 异步支持完善、migration工具成熟 |
| Python → Node | 不走 | FastAPI原生async性能足够 |

## 附录：思考——什么让产品跨越10年？

### 穿越周期的产品特征

1. **数据复利**：用得越久，价值越大（记忆积累）
2. **低切换成本诱惑**：用户想离开，但舍不得那些记忆和画像
3. **简单内核**：核心功能10年后仍然成立（对话+记忆）
4. **用户掌控**：数据可带走，用户无锁定恐惧
5. **避免时髦**：不追RAG、Agent、Workflow这些热词——把"记住用户"这件事做到极致

### 竞品分析 —— 为什么现在不做功能堆砌？

| 产品 | 为什么用户离开 |
|------|---------------|
| Notion | 太重，组织成本 > 使用收益 |
| ChatGPT | 不记得昨天的对话 |
| 各种AI助手 | 浅层集成，用完就走 |
| 日记App | 需要主动记录，人太懒 |

**Personal OS 的护城河**：对话零门槛 + 记忆复利 + AI人格一致性。

用户用了一年之后，里面有他一年的记忆、决策、成长轨迹。切换成本不是数据导出——是**失去一个认识他一年的人**。
